# ScamSniffer — AI-Based Phishing Detection System

## 1. Project Overview

ScamSniffer is an AI-based phishing detection project designed to help users identify potentially malicious URLs and suspicious messages.

The system uses machine learning models to analyze URLs and text, helping users recognize common phishing and scam indicators before interacting with potentially dangerous content.

The project uses Python and Streamlit to provide a user interface for phishing detection.

### Main Objectives

- Detect potentially malicious URLs.
- Analyze suspicious messages and identify possible phishing attempts.
- Provide understandable detection results.
- Reduce the risk of users interacting with phishing links and scam messages.
- Build a modular, testable, and maintainable cybersecurity application.
- Establish a foundation for future improvements to detection accuracy and explainability.

**Important:** ScamSniffer provides an automated risk assessment. Its results should not be treated as a guarantee that a URL or message is safe or malicious.

### Main Components

#### 5.1 Streamlit Interface

The Streamlit application provides the user-facing interface.

Its entry point is:

```text
app/main.py
```

The interface accepts user input and presents the detection results produced by the application's detection logic.

#### 5.2 Detection Component

The detection logic is maintained in:

```text
src/detector.py
```

This component contains detection-related logic, including text-verdict handling.

For text detection, the current verdict logic considers both the model's prediction and certain message indicators.

When urgency-related language and credential-request indicators are both present, the logic assigns a phishing verdict. Otherwise, the model's prediction is used to determine the verdict.

This is a heuristic-based decision rule and should be evaluated against representative legitimate and phishing messages.

#### 5.3 Active URL Model

It is loaded successfully using Joblib.

#### 5.4 Active Text Model

## 9. Training and Model Evaluation

Model training and evaluation should be performed separately from the application's normal detection workflow.

The project contains training-related scripts, including:

```text
scripts/train.py
scripts/train_phiusiil.py
```

The first script is associated with the main training workflow, while the second is associated with the separate PhiUSIIL experiment.

Before running either script, inspect its arguments, input requirements, output paths, and training procedure.

Do not assume that both scripts use the same datasets or produce interchangeable models.

### Recommended Evaluation Metrics

The following metrics are useful for phishing detection:

**Accuracy:** The proportion of all predictions that are correct.

**Precision:** The proportion of predicted phishing cases that are actually phishing.

**Recall:** The proportion of actual phishing cases detected by the model.

**F1-score:** A combined measure of precision and recall.

**False-positive rate:** The proportion of legitimate samples incorrectly classified as phishing.

**False-negative rate:** The proportion of phishing samples incorrectly classified as legitimate.

For cybersecurity applications, false positives and false negatives should both be investigated. High accuracy alone may hide weaknesses in detection.

Evaluation should use appropriate training and test separation to avoid misleading results caused by data leakage.

## 10. Security and Privacy Considerations

ScamSniffer is intended to analyze URLs and text supplied for detection.

### Safe Processing Principles

- Treat user-provided URLs and messages as untrusted input.
- Validate inputs before processing them.
- Handle malformed input without crashing the application.
- Avoid logging complete messages or sensitive information unnecessarily.
- Do not expose local filesystem paths or internal error details to users.
- Avoid executing content contained in suspicious messages.
- Keep dependencies and model artifacts under version control and change review.
- Test boundary conditions and malformed inputs.

### External Network Requests

The application should not automatically open suspicious URLs simply to determine whether they are malicious.

Any future network-based analysis should be explicitly designed with safeguards against server-side request forgery, access to private network resources, unwanted redirects, and other risks.

Whether the current implementation performs any DNS lookups, HTTP requests, or other network activity must be confirmed by inspecting the source code.

### Input Size Limits

Input length limits can help reduce resource exhaustion and improve reliability.

The exact limits for URL and message inputs should be documented only after verifying the implementation.

### Privacy

Users should avoid submitting passwords, authentication tokens, private correspondence, financial information, or other sensitive data unless the application explicitly supports the required privacy and security protections.

Data retention and logging practices should be reviewed before deploying the application for public use.

## 11. Current Limitations

The current project should be treated as a machine-learning-assisted phishing detection tool rather than a complete security guarantee.

Potential limitations include:

- Legitimate websites may be incorrectly flagged.
- New phishing techniques may not resemble the training examples.
- Message wording can change the model's prediction.
- Detection performance depends on the quality and representativeness of the training data.
- A model's performance on one dataset may not generalize to real-world traffic.
- The application may not identify every malicious URL or scam message.
- Model predictions may require additional explanation to be useful to non-technical users.

The active models should be evaluated periodically using fresh, representative samples.
